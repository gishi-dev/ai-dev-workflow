# 自動ランナーの流れ

人がIssueやPRにラベルを付けると、ランナーが定期的に（3分ごと）確認して作業を進めます。
対象がないときはAIを起動しません。

## 状態ラベル

| ラベル | 付ける人 | 意味 |
|---|---|---|
| `ai:ready` | 人 | このIssueを着手してよい |
| `ai:working` | ランナー | 実装・自己レビュー中 |
| `ai:waiting` | ランナー | 作業の途中でAIが質問し、本人の回答を待っている |
| `ai:blocked` | ランナー | 自己レビューで指摘が残った、または作業を続けられないため停止 |
| `ai:review` | ランナー | PRを作成し、人の確認を待っている |
| `ai:merge-approved` | 人（PRに付ける） | マージしてよい |

`ai:ready` と別の状態ラベルが重なったIssueは、処理の対象から外します。
着手とマージのラベルは、承認者として設定した人が付けたものだけを有効にします。

## Issueの処理

1. `ai:ready` のIssueを1件ずつ取り、`ai:working` に変える。二重に着手しないよう、ロックを取ってから進める。
   Issue本文に「前提：#番号」と書かれていれば、そのIssueが閉じるまで着手せず、待っていることをIssueにコメントする。
2. 最新の `main` から作業ブランチと専用のworktreeを作る。
3. AIがIssueの範囲で実装し、既存テストや静的検査で確認する。AIの実行環境には、GitHubやDBの認証情報を渡さない。
4. 別のAIが、読み取り専用で差分をレビューする。指摘があれば修正させ、再レビューする（最大3回）。
5. 作業の途中で人の判断が必要になったら、AIがIssueに質問を書き、`ai:waiting` にして回答を待つ。
6. 最大回数のレビューでも指摘が残る場合は、`ai:blocked` にして停止する。PRは作らない。
7. レビューを通過したら、追加した行とPR本文を、よくある認証情報の形式で検査する。疑わしいものがあれば停止する。
8. ランナーがコミット・push・PR作成を行い、`ai:review` にする。PR本文には、変更内容・確認結果・自己レビューの回数を載せる。

## 質問への回答と、停止からの再開

- `ai:waiting` のIssueに本人がコメントで回答すると、質問・回答・元の要件・作業中の差分を照合してから作業を再開する。
- 停止したときは、worktreeの状態と残った指摘を記録する。
- `ai:blocked` のIssueは、人が内容を確認して `ai:ready` を付け直すと、worktreeの差分が停止時から変わっていないことを確かめてから、保存済みの差分を修正して再開する。
- worktreeに想定外の変更がある場合は、上書きせずに止める。

## マージ

人がPRを読み、`ai:merge-approved` を付けると、次の条件をすべて確かめてからマージします。

- PRがOpenでマージ可能であり、Issueが `ai:review` である。
- PRの先頭コミットが、PR作成時に記録したものと一致する（後から追加されたコミットは自動で取り込まない）。
- GitHubのチェックに、失敗や未完了がない。
- 作業ブランチとworktreeが対応しており、未保存のファイルや使用中の処理がない。
- DBマイグレーションや依存関係の変更を含まない（含む場合は人が手動で取り込む）。

条件を満たせばマージし、作業ブランチ・worktreeを片付けて、主の作業場所の `main` をfast-forwardで同期します。
確認できない条件（チェックが未完了など）があれば、承認ラベルを残して次の巡回で確かめ直します。
